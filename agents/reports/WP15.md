## First spike after D13: can a server route set `_owner`?

R15.2 and R15.10-11 depend on this. Use a throwaway collection, never the live `lms-*` rows.

1. In the dashboard, create collection `wp15-owner-spike` with field `note` (TEXT) and permissions **Admin / Site member author / Admin / Admin**.
2. Pick a test member (a Camren test account) and note its member ID (Dashboard → Contacts, or `GET /members/v1/members/my` with its token).
3. Admin token:
   `curl -s https://www.wixapis.com/oauth2/token -H 'Content-Type: application/json' -d '{"grant_type":"client_credentials","client_id":"<PUBLIC_WIX_CLIENT_ID>","client_secret":"<WIX_CLIENT_SECRET>","instance_id":"93f9dffd-79fb-4bea-94fa-810eef3397fe"}'`
4. Insert as admin with an explicit owner:
   `curl -s https://www.wixapis.com/wix-data/v2/items -H "Authorization: $ADMIN" -H 'wix-site-id: 93f9dffd-79fb-4bea-94fa-810eef3397fe' -H 'Content-Type: application/json' -d '{"dataCollectionId":"wp15-owner-spike","dataItem":{"data":{"note":"spike","_owner":"<MEMBER_ID>"}}}'`
   **Pass 1:** the returned `dataItem.data._owner` equals `<MEMBER_ID>`, not the app's ID.
5. Update it as admin (PUT with `data` including `_owner`), then GET it. **Pass 2:** `_owner` is unchanged.
6. Sign in as the test member on the real-mode app (localhost with the client ID). In devtools, take the access token from the `/api/session` response (`accessToken.value`), then:
   `curl -s https://www.wixapis.com/wix-data/v2/items/query -H "Authorization: <MEMBER_ACCESS_TOKEN>" -H 'Content-Type: application/json' -d '{"dataCollectionId":"wp15-owner-spike","query":{}}'`
   **Pass 3:** the row is returned.
7. Repeat step 6 with a second member's token. **Pass 4:** no rows.
8. Delete the collection.

If Pass 1 or 3 fails, Wix will not let a server route give a member ownership. Then the author-read design for accounts, players and the mirror collections does not hold. The fallback is family read routes on the server (e.g. `GET /api/family`, `GET /api/players/:id/events`) that query with the admin token and filter by `accountId`. Ask before building it.

## Found, not fixed (outside my files)

- **Client-side open redirect in `src/pages/login.astro` (lines 58-71) and `src/pages/verify.astro` (line 61).** They pass raw `?next=` to `location.replace(next)` / `location.href = next`, so `/login?next=//evil.com` leaves the site for an already-signed-in user (and in demo after the demo button). A `javascript:` value may also run script. The fix is one line each:
  ```js
  import { safeNext } from '../lib/server/policy.js'; // pure, browser-safe
  const next = safeNext(params.get('next'), location.origin);
  ```
  Neither file is in my ownership list or any parallel package's, so I left it for whoever owns auth pages.
- The grown-up gate renders twice on a direct load of `/family/players/*`, because `init` runs on both the first call and `astro:page-load` before the `wp4Bound` guard. This is cosmetic and pre-existing. My e2e works around it.
- In Class mode, `me.astro`'s avatar change calls `updatePlayer` for a non-family child. In real mode that is now a 403 from `PATCH /api/players`, which is the intended outcome; it also failed before under author-update. The page doesn't catch it.
